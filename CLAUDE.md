# Working on the software factory

- Everything runs through uv: `uv run pytest -q`, `uvx ruff check .`. Python 3.13, line length 100, double quotes. Prose (docs, skills, manuals) soft-wraps one paragraph per line — never column-wrapped.
- The engine stays dumb: `src/factory/` is a deterministic state machine — no natural-language interpretation belongs there. All language understanding lives in `.claude/` (skills, commands). `line.yml` is the single source of truth for the line's shape.
- Dispatcher discipline: `next_action()` stays pure (decide, never mutate); mutating operations validate and `route()` *before* `store.save()`, so bad input can never persist a half-applied item; history is append-only — corrections are new events, not edits.
- Never lose input silently: anything the system accepts must land somewhere durable (a write-only field is a bug — we've shipped three), and anything it can't use must be rejected or warned about at the boundary, never ignored. When two layers need the same rule, give it one home and make both consume it (e.g. `GateDecision.is_steer` in `model.py`).
- One consumer per template: `templates/` holds only files a live component fills in or points at (rule and table in `templates/README.md`).
- The CLI's `--help` is its source-of-truth documentation — flag docs live in the parser, and `.claude/` recipes stay thin pointers. Every bug fix ships with a regression test, and every test carries a one-line docstring naming the invariant it pins.
- For `cli.py` and `install/` changes, green tests aren't done: also drive the real command (a temp factory root for the CLI, a scratch repo for install — including the reinstall and uninstall paths). The last several real bugs were invisible to the suite.
- Adding a rule for the *driving* agent? Put it where it's guaranteed to load at the moment it matters: station requirements in that station's SKILL.md (self-guarding — see the isolation guards in code-review/verify), driver protocol in `.claude/commands/factory.md`, and the board hook + installed CLAUDE.md block stay discovery pointers, never rulebooks (they'd drift).
- Two skill layers, kept apart: *portable* skills (`write-product-spec`, `write-tech-spec`, `council`) speak in generic roles (author, reviewer, verifier) so they stay reusable and don't confuse an agent about factory-specific terms; *factory-native* files (station skills, the `factory-spec` coordinator, `line.yml`) own the station/gate vocabulary and the wiring between stations. Don't leak factory jargon into a portable skill's body, and don't restate the wiring outside its one home — a single labeled pointer in the portable skill's `description` is the most coupling allowed.
- Soft directives by default: in `.claude/` guidance prefer "prefer/avoid" over "never/must". An absolute is for a rule guarding a garbage-in or safety failure whose reason you can name (e.g. "never spec from a title alone"; "a checker never shares the builder's session" — that's self-grading); blanket strict verbiage elsewhere just makes the driving agent brittle and second-guess sound judgment.
- Docs are living artifacts: a change that affects behavior or design updates whatever it touches under `docs/` and `FACTORY-MANUAL.md` in the same change — they are how human adopters and future agents understand the factory and its why, so a stale doc is a bug. If the line's shape or flow changes, also update `docs/diagram.md` (the Mermaid source of truth) and re-render `docs/diagram.png` with `scripts/render-diagram.sh`.
- `docs/OPTIMIZATION-AREAS.md` is a deliberate log, not a wishlist: add an entry only when you can state both the current cost and a plausible direction against the existing architecture; remove one only when it shipped or stopped being true.
- The install layer is a contract: any change to what ships into target repos (`.claude/` skills/agents/commands/hooks, the root config files, `templates/`, the CLAUDE.md block, hook behavior) must be checked against `install/install.py` (the `CLAUDE_ITEMS`/`ROOT_FILES` lists, manifest and uninstall logic), `install/README.md`, and the `install-factory` skill — for functionality, compatibility, and verbiage. Retiring a file the toolkit used to ship — especially one *inside* a still-shipped directory, which the manifest tracks only by its parent — means adding it to `install.py`'s `_RETIRED_PATHS`, or an upgrade orphans it in adopter repos.
- Versioning is a coarse adopter signal, not strict semver — `pyproject.toml`'s `version` is the single source (`_toolkit_version()` reads it; the install manifest stamps version + commit, so the commit carries the precision). Bump a **minor** (pre-1.0) when the install contract's *shape* changes — files shipped or retired, a station/line change, hook behavior; a **patch** for a fix worth pulling that keeps the same shape (an engine, installer, or shipped-skill bug fix, same interfaces and file set); internal-only changes (refactors, docs, tests) ride the commit SHA with no bump.
- Reading path for the codebase: `docs/CODE-TOUR.md`. Architecture rationale: `docs/ARCHITECTURE.md`.
